# NIBRS hand-traced correctness set (phase 1)

Expected answers computed from raw NIBRS segment rows, independent of any engine. Every new NIBRS engine path
(canonical build, semantic layer, plan compiler, accelerators) must reproduce them before shadow comparison.
Plan: `docs/superpowers/specs/2026-10-27-nibrs-engine-restructure.md`, phase 1.

## What is here

| Path | What |
|---|---|
| `CASES.md` | every case: the question, the interpretation, the hand trace, what the answer must and must not do |
| `extracts/` | raw segment rows, read from nibrs.db's raw tables (never a `summary_*` table) |
| `extracts/micro/` | every segment of seven real incidents (incidents, offenses, victims, offenders, property, arrestees) |
| `extracts/QUERIES.sql` | the exact read-only queries that produced the extracts |
| `expected/micro.json` | hand-traced expectations for the seven incidents |
| `expected/N*.json`, `Z`, `D`, `R` | expected answers for the named cases, written by the reference script |
| `../../nibrs-correctness-reference.py` | the reference computation: stdlib Python, one loop per case, reads only `extracts/` |

```bash
python scripts/nibrs-correctness-reference.py --check
```

`--check` recomputes every expected file from the extracts, cross-checks the hand-traced micro counts against the
micro extract, and fails on any difference.

## Independence

- Inputs are raw segment rows. No summary table, no NIBRSAI library code, no SQL generated by an engine.
- The micro cases are traced by hand (CASES.md shows each row). The script only checks the hand counts.
- The named cases are too large to trace row by row (Baltimore alone has 26,702 offenses), so each has:
  - a reference loop simple enough to review line by line;
  - one month traced by hand, or micro incidents that show the rule;
  - a recount against today's live answer, which proves only that the raw rows and the summary tables agree.
    Every difference found is explained in CASES.md.

## Source and its limits

- Read 2026-10-28 00:45-01:30 UTC from `/opt/nibrs/nibrs.db` (refreshed 2026-10-16), read-only, `nice -n 19`, each
  query filtered by ORI + data year + offense code on an indexed column, with the release and maintenance locks
  checked free before every read. Not on the 15th-19th or November 3-4.
- nibrs.db is itself a parse of the FBI master files, and it is lossy where the canonical build will not be:
  - victims keep 3 of the 10 connected offenses and 3 of the 10 offender relationships
    (M4 needs relationships for offenders 04-06: marked `PENDING_MASTER_FILE`);
  - the incident segment's header counts are misparsed: `total_victim_segments` is 0 and `total_offender_segments`
    reads 10-60 on every micro incident, against 1-6 actual offender rows. No case uses them.
  - five 2023 Baltimore incidents are stored twice with every segment identical (N3).
- When the canonical build reads the master files, each case is re-derived from the master-file lines for the same
  incident keys. A difference is either a nibrs.db loss listed here or a defect in one of the two parses.

## Reporting status in phase 1

The BH month indicators are not decoded yet (shared spec r4, D6), so the only evidence is crime rows:
- a month with rows for the agency is `REPORTED_CRIMES` (this does not prove the submission was complete);
- a month without rows is `UNKNOWN`, never 0 and never `NOT_REPORTED`;
- a filtered measure with no rows in a `REPORTED_CRIMES` month is `UNKNOWN` for that measure (case Z), with the
  value it takes once the month is evidenced complete recorded beside it.

When the BH indicators are decoded, the status-dependent fields are re-derived; the counts do not change.

## Month and year

Months are incident-date months. In every extract the data year equals the incident-date year (checked for all
three agencies, 2017-2026), so no case depends on how a late-reported incident is placed. A future case must cover
that once the canonical layer can hold one.
